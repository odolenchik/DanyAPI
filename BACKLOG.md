### DeepSeek: не перезагружать вложения, уже вложенные в сессию

Сейчас вложения грузятся на апстрим заново на **каждом** запросе, даже когда
сессия та же и файл в ней уже есть. `_collect_attachments`
(`danyapi/api/attachments.py:36`) обходит всю историю сообщений и собирает все
`image_url`, а `_upload_attachments` (`attachments.py:88`) грузит каждое
вложение с нуля, с новым PoW-челленджем на каждый файл. Вызов —
`danyapi/api/openai.py:613-617`. Дедупа по содержимому и переиспользования
`file_id` нет.

Проверено живьём (nonce-тест, сервер на 6660): картинка со случайным кодом
`68K5U2` отправлена на ходу 1, на ходу 2 картинка **не** отправлялась, тот же
`session_id` — модель назвала код правильно. В логе на ходу 2 нет ни загрузки,
ни `upload file OK`, только `completion OK`. То есть DeepSeek хранит вложение
внутри сессии, и повторная отправка — чистая трата трафика и PoW.

Масштаб: N ходов с картинкой в истории = N загрузок (линейно). Картинка 10 МБ
на 20 ходов ≈ 200 МБ лишнего трафика. Побочно: загрузка часто падает с
`40301: INVALID_POW_RESPONSE` и уходит в ретрай — меньше загрузок, меньше сбоев.

Решение: хранить в сессии набор отпечатков (хешей) уже вложенных файлов.
При запросе считать хеш каждого вложения и грузить только те, которых в сессии
нет; новые — отмечать. Если сессия новая (или её нет) — грузить всё, как сейчас.

Важная оговорка: «просто не отправлять» само по себе не годится — сессия может
исчезнуть (LRU `DANYAPI_SESSION_CACHE_SIZE=128`, TTL 3600 с, промах
фингерпринта в `ContextIndex.lookup`). Тогда вложения на той стороне уже нет,
и его надо загрузить заново, иначе модель его не увидит.

Места правки: `danyapi/sessions.py:38` (`SessionRegistry._serialize` —
добавить список отпечатков), `danyapi/api/attachments.py:36,88` и
`danyapi/api/openai.py:613-617`. Затрагивает контракт с апстримом
(`ref_file_ids`), поэтому нужен живой E2E: 3+ хода с картинкой в истории,
проверить, что загрузка одна, а модель по-прежнему видит картинку.

### БАГ: `invalid message id` — битый parent после rate-limit (не-стриминг)

Порядок операций в не-стриминговом пути перевёрнут относительно стримингового:
при rate-limit хинте в сессию записывается id сообщения, которого апстрим не
сохранил.

Не-стриминг, `danyapi/api/streaming.py:693-710`:
```python
account.sessions.touch_last_message(session_key, rec.id or response_message_id)  # 694 — СНАЧАЛА
...
if not (rec.content or rec.reasoning) and rec.hint_error:                        # 699 — ПОТОМ
    raise HTTPException(429, _busy_error_body(rec))                              # 710
```

Стриминг, `danyapi/api/streaming.py:1199-1242` — тот же код, но в правильном
порядке: сначала `if ... hint_error: ... return` (1199-1239), и только потом
`touch_last_message` (1242).

Последствие: при rate-limit хинте сервер запоминает несуществующий id и отдаёт
429. Следующий запрос берёт его как `parent_message_id` (`_prepare_session`,
`danyapi/api/deepseek.py:251` — `return session, session_key,
session.last_message_id`) → апстрим отвечает `DeepSeek error 26: invalid message
id`. Ошибка попадает в retryable (502), уходит в 5 повторов с тем же битым id,
сессия остаётся сломанной — баг самоподдерживающийся.

Воспроизведено живьём 2026-09-23 (сервер на 6660): после `completion OK (731ms)`
пришёл rate-limit хинт → 429; следующий запрос в ту же сессию дал
`502 DeepSeek error 26: invalid message id`, затем 5 ретраев по 502.

Фикс: перенести проверку `hint_error` **до** `touch_last_message` (как в
стриминге). Плюс не запоминать `rec.id`, если ответ пустой.

### DeepSeek: хвост инструментов переотправляется целиком на каждом шаге

`_render_tool_tail` (`danyapi/tools/prompt.py:245`) собирает **все** сообщения
ассистента и результаты инструментов после последнего user-сообщения. На шаге k
туда попадают все k−1 предыдущих обменов, и весь этот текст уходит в апстрим
заново — в ту же сессию, где он уже есть.

Рост квадратичный: шаг 1 → 1 обмен, шаг 2 → 2, шаг 19 → 19.

Измерено на `tooltrace.ndjson` (4660 запросов, 159 сессий):
- шагов-продолжений инструментов: **2860** (61% всех запросов)
- отдельных tool-раундов: 732, самый длинный — **33 шага**, медиана 2
- отправлено единиц промпта: 12 773; нужно было бы (только новый обмен): 2 860
- **перерасход 4.5x**

Прямое подтверждение в логе — 280 пар, где предыдущий промпт **целиком
содержится** в следующем (сравнение по непересечённым промптам, 1269 пар).

Хвост обрезается до `MAX_APPEND_PROMPT_CHARS = 52000` (`prompt.py:10`), то есть
на длинном раунде каждый шаг — до ~13k токенов впустую.

НЕ ПРОВЕРЕНО ЖИВЬЁМ: можно ли хвост вообще не слать. Логика та же, что с
вложениями (там подтверждено nonce-тестом), но здесь доказательства нет. Нужен
тест: отправить минимальный промпт на втором шаге tool-раунда и проверить,
видит ли модель результат предыдущего инструмента. Тест 2026-09-23 сорвался на
rate-limit/`invalid message id` и до этого вопроса не дошёл — переписывать с
разнесением запросов по времени.

### DeepSeek: картинки хешируются целиком на каждом запросе

`context_sequence` (`danyapi/tools/prompt.py:170`) считает sha256 по содержимому
первых сообщений, а `_content_fingerprint` (`prompt.py:139`) включает в отпечаток
**весь** data-URI картинки, а не хеш. Замер на картинке 11 МБ:
- `_content_fingerprint`: 0.005 с, вернул 11 534 367 символов
- sha256 поверх: 0.017 с

Итого ~0.022 с CPU и 11.5 МБ строки в памяти на **каждый** запрос с картинкой,
даже когда сессия уже найдена по этому самому отпечатку. Фикс: хешировать хеш
содержимого (или длину + первые байты), а не весь data-URI.
