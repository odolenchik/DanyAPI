### Определить точные пороги rate-limit DeepSeek (начато 2026-09-23)

Замеры сделаны, но **не доведены** — нужно продолжить с того места.

**Что уже измерено** (один аккаунт, одна сессия `62f4dc87`, non-stream, модели
`deepseek-v4-pro`, запросы «Reply with exactly: OK»):

| Пейсинг | Итог | `starts_*` при первом падении |
|---|---|---|
| выключен, human delay 0 | 7 OK, падение на 8-м | `10s=8` |
| `MIN_REQUEST_INTERVAL=2.0` | 9 OK, падение на 10-м | `30s=10 60s=11` |
| `MIN_REQUEST_INTERVAL=3.0` | 10 OK, падение на 11-м | `60s=11` |
| `MIN_REQUEST_INTERVAL=6.0` | **16 OK, 0 падений** | — |
| `MIN_REQUEST_INTERVAL=8.0` (текущий `.env`) | **10 OK, 0 падений** | — |

Гипотеза: лимит ≈ **10–11 запросов за скользящее окно 60 с**. В двух независимых
чистых прогонах первый хинт приходил ровно на `starts_60s=11`. 6 с/запрос (10/мин)
— впритык; 8 с/запрос (7.5/мин) — с запасом.

**Важно: контаминация.** Прогон с интервалом 2 с сразу после агрессивного
показывает `starts_60s=31` — аккаунт был ещё под блоком, первые 8 падений к
интервалу отношения не имеют. Перед каждым замером нужен poll до первого 200.

**Что не проверено:**

1. **Граница 3–6 с.** Шаг 4.0 и 5.0 с не прогнан (сервер упал по таймауту задачи).
2. **`MIN_END_GAP` в чистом виде.** Все прогоны шли с `MIN_END_GAP=0` и короткими
   запросами (~1 с). Сценарий, ради которого фикс и делался (цепочка длинных
   запросов ~80 с), не воспроизведён вообще.
3. **Длительность блока.** В тесте аккаунт остывал за секунды (poll дал 200 сразу
   после 60 с паузы). Пользователь наблюдает блокировки **10–15 минут** —
   расхождение не объяснено. Возможные причины: другой тип блокировки при
   длительном превышении, привязка к устройству/аккаунту, а не к темпу; влияние
   параллельных копий DanyAPI. Разобраться отдельно.
4. **Параллельные запросы.** Все замеры последовательные, в один поток.

**Инструмент:** `/tmp/ds_stress.py` (probe | seq <n> [delay] | poll <interval> <max>).
Пинит `session_id` через `/tmp/ds_stress_session.txt`, читает хинты из
`/tmp/danyapi3/danyapi.log`. Запускать против сервера на 6660.

```bash
cd /home/odolen/ssd_new/DanyAPI3
# сервер с нужными настройками (пример: без пейсинга)
DANYAPI_LOG_FILE=/tmp/danyapi3/danyapi.log DANYAPI_MIN_REQUEST_INTERVAL=0 \
  DANYAPI_MIN_END_GAP=0 DANYAPI_MIN_START_GAP=0 DANYAPI_HUMAN_DELAY_MIN=0 \
  DANYAPI_HUMAN_DELAY_MAX=0 .venv/bin/python -m danyapi
# замер
.venv/bin/python /tmp/ds_stress.py poll 5 20   # дождаться остывания
.venv/bin/python /tmp/ds_stress.py seq 16 4.0  # прогон с интервалом 4 с
```

**Текущий вывод по `.env`:** `MIN_REQUEST_INTERVAL=8.0` достаточен для частотного
сценария, поднимать не нужно. `MIN_END_GAP=5.0` оставлен по расчёту и пока не
подтверждён замером.

### Retry на нераспарсенный tool-call (заход 1 сделан 2026-09-30)

**Проблема.** Когда `parse_tool_calls` возвращает `None` (`unparsed`), Dany отдаёт
клиенту сырой текст как обычный ответ. При этом ремонт (`_repair_tool_calls`)
уже есть, но срабатывает **только** когда парсинг прошёл, а упала валидация схемы.
То есть parse-фейл не ретраился вообще.

**Что сделано (заход 1).**

- Гейт `should_retry_unparsed` (`danyapi/tools/validate.py`): `tool_choice`
  форсирует вызов (`"required"` / именованная функция) → ретраить всегда;
  `"none"` → никогда; `auto`/не задан → только при `DANYAPI_TOOLCALL_RETRY`
  **и** вердикте классификатора `json_malformed`; обычная проза
  (`no_tool_call`) не ретраится.
- Промпт parse-фейла `build_unparsed_repair_prompt` (`validate.py`).
- Общий транспорт обоих ретраев — `_retry_tool_call`, гейт — `_repair_unparsed`
  (`danyapi/api/streaming.py`), проведено во **все 4 сайта парсинга DeepSeek**
  (non-stream, stream, оба compact-пути). Стрим: hook — до первой отправки
  `content_buf` клиенту.
- Успешный parse-fail-ретрай помечается `continuation`-событием в tooltrace.
- Env-флаг `DANYAPI_TOOLCALL_RETRY` (`danyapi/config.py`, off по умолчанию).
- Тесты: `tests/test_tools_api.py` (+6), `tests/test_validate.py` (+2),
  `tests/test_config.py` (+2).

Верификация: `ruff check` + `ruff format --check` + `pytest -q` → **1204 passed**,
`arch-check` OK.

**Что осталось:**

1. **Qwen и zai.** Скоуп захода 1 — только DeepSeek; у Qwen/zai своего repair нет.
2. **Замер.** Посчитать долю tool-раундов с манглом, чтобы решить, оправдан ли
   ретрай для `auto` (каждый retry = +1 upstream запрос, PoW, токены).
3. **Дублирование 4 сайтов парсинга** — минус; чище вынести «parse → validate →
   repair → unparsed-retry» в один async-хелпер. Рефакторинг — отдельной задачей.

### `{"tool": ..., "why": ..., "goal": ...}` без аргументов (найдено 2026-09-25)

DeepSeek иногда отдаёт объект вида `{"tool":"port_scan","why":"...","goal":"..."}`
— с именем инструмента, но **без аргументов вообще**. Сейчас такой объект
корректно остаётся `unparsed:no_tool_call` (tooltrace `9c9a2f94`, `8f52553d`).

Похоже на план-документ (обоснование следующего шага), а не на готовый вызов,
поэтому парсить его как tool-call, скорее всего, не нужно. **Проверить:**
объявлялся ли такой формат в промпте клиента, или это свободная импровизация
модели. Если импровизация — оставить как есть; если это его штатный «план» —
решить, должен ли Dany его как-то транслировать.
